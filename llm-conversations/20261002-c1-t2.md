## 串行写是很合适的起点，但客户端的“先读后写”仍是另一回事

我赞成你目前的选择。这不只是降低实现难度，也给模型提供了一个非常清楚的基础：每次处理一个 commit 时，已经接受的历史只有一个确定的末端，candidate state 也只有一个明确的起点。SQLite 本身同样以串行化写入实现其事务隔离；WAL 模式则允许读取与这个单一 writer 并行进行，因此与你设想的初期架构是相配的。[SQLite](https://www.sqlite.org/isolation.html?utm_source=chatgpt.com)

这里我会稍微区分一下两个保证：串行化决定 commit 之间如何先后发生，atomic transaction 保证一个 commit 内部不会只完成一部分。两者在 Zeon 中配合起来，才构成你希望的写入语义。SQLite 可以承担后者，不需要你自己从磁盘写入开始重新实现。[SQLite](https://www.sqlite.org/atomiccommit.html?utm_source=chatgpt.com)

还有一个由你的决定直接推出来的要求：**validator 不能把最终一致的读取缓存当作当前权威状态。** 当前状态在本质上仍然可以是缓存，但进入写入路径时，它必须已经覆盖所有先前接受的 commit，或者能够补齐尚未应用的部分。特别是 validator 使用的 reducer 结果，也必须在 candidate state 上计算，不能拿一个落后的点赞数、投币数直接判断。

这也让旧文档里有一处很小、但值得记下的衔接问题：投币示例写的是检查 `votes + 当前值` 是否超过 `vote-max`。如果 validator 中读到的 `votes` 已经来自应用本次提交后的 candidate state，那么应直接检查 `votes <= vote-max`，否则会重复计入本次投币。原公式成立的前提，是其中的 `votes` 指向提交前的值。这不影响模型方向，只需要之后把 validator 的读取上下文与示例统一起来。

至于我之前那句“仅当我读到的版本仍然有效时接受本次提交”，确实是我说得太抽象了。它并不假设客户端持有完整 repo，甚至不要求客户端持有整个对象。

例如，你读取一个对象的标题，得到 `"A"`，同时得到这个属性的最后修改指针 `p10`。你在编辑框里修改标题的过程中，另一个人已经提交了 `"B"`，最后修改指针变成 `p11`。随后你的客户端提交 `"C"`。即使服务端完全串行地处理这两个 commit，它仍然会先接受 `"B"`，再接受 `"C"`；整个过程没有违反事务性，但你可能在不知道别人已经修改的情况下覆盖了对方的工作。

可选的 precondition 就是在你的提交里附上：“只有这个标题的最后修改指针仍然是 `p10`，才接受这次修改。”服务端排到这次提交时发现它已经是 `p11`，就拒绝并报告冲突。客户端只需要保留一个随读取结果返回的 token，不需要复制 repo，也不必要求整个 repo 在此期间都没有变化。HTTP 的 `If-Match` 处理的就是这一类 lost update 问题，这里只是借它说明语义，并不是建议 Zeon 一定采用 HTTP。[RFC 编辑器](https://www.rfc-editor.org/rfc/rfc9110.html)

所以，**服务端串行写解决的是“两个修改如何执行”，这个 precondition 解决的是“客户端作出修改决定时依据的事实是否仍然成立”。** 它可以是可选能力，不必改变 `mut` 默认取最新提交的规则。而且它应当针对写入前的权威状态检查，与业务 validator 检查 candidate state 并不冲突：一个确认操作前提，一个确认操作结果。

将来真的需要优化时，也可以先把解码、签名验证、不依赖 repo 状态的静态检查放到串行通道之前并行执行，继续保留最终校验与接受的串行性。没有必要一开始就判断任意两个 validator 的依赖是否完全无关。

## 服务端时间戳解决了客户端乱序，但还不能单独承担排序

把客户端时间和服务端时间分开，我认为是一个合理的调整。不过这里还剩下两个需要分开的概念：**发生时间与接受顺序，以及客户端签署的内容与服务端补充的内容。**

先说顺序。服务端的 wall clock 也可能回拨；时间 API 的精度也不等于每次调用都能获得一个不同的时间值。官方时间 API 文档明确提醒，系统时钟被向后调整时，后一次读取可能小于前一次。[Python documentation](https://docs.python.org/3/library/time.html)

因此，即使只有一个 writer，也最好不要把“时间戳严格递增”当成自然成立的条件。尤其是，**如果比较 commit ID 时仍然先比较时间戳，那么仅仅递增后面的序列码，不能修复时间戳回拨导致的乱序。**

我个人更偏向把 repo 内的接受顺序单独确立为一个持久化的递增 position，让 timestamp 负责记录时间。它不一定需要成为一个全新的公开字段，也可以重新明确现有序列码的职责与排序规则；关键是，不让“时间”和“次序”必须由同一个数值同时保证。这个 position 之后还可以自然地作为缓存进度、历史读取边界和恢复游标。

另一条可行路线，是保持时间戳优先的 ID 排序，但分配 ID 时将时间戳钳制为不小于上次值，在时间没有前进时增加序列码。这样也能得到稳定顺序，只是此时 ID 中的 timestamp 已经带有逻辑时间的性质，不再严格等于那一刻读到的 wall clock。跨重启时也必须恢复此前的分配状态。两种方案都能做；就你追求语义清楚的取向而言，我更喜欢前一种。

签名方面，你现在的方案可以进一步整理成两个层次：客户端签署“我请求对这个 repo 作出这些修改”，服务端在接受后补充“这个请求成为了哪个 commit，以及它处于什么位置”。客户端的签名输入可以包含 repo identity、operator、客户端时间、请求标识、修改内容，以及可选的 preconditions；服务端生成的最终 commit ID 则属于接受记录。

这里有一个需要明确的边界：客户端时间与服务端时间很接近，并不会让客户端签名自动覆盖服务端时间或最终 commit ID。未纳入签名输入的字段，改变后也不会导致这份签名验证失败；签名覆盖范围需要明确规定。[RFC 编辑器](https://www.rfc-editor.org/rfc/rfc9421.html)

这不代表你的方案有问题。如果目标是证明“这个 operator 确实授权过这些修改”，客户端签名可以承担这个职责；如果还要让导出的历史能够独立证明“服务端确实把它作为这个 ID、按这个位置接受了”，那是服务端接受记录的认证问题，可以另行设计，不必勉强让一份客户端签名证明两件事。

时间差检查也建议在实现中与密码学验签区分开：签名正确，但请求超出允许时间窗口，仍然可以拒绝，只是拒绝原因是 freshness 检查失败。这样以后重建历史时就不会混淆“当年是否应当接受这个请求”和“今天是否还允许把它当成新请求提交”。已经接受的旧 commit 不应因为今天已经过去很久而失效。

同时，时间窗口不能代替请求去重：同一份合法请求在窗口内发送两次，依然可能两次通过验签。签名协议中的 nonce 与时间限制分别处理不同方面的 replay 风险。[RFC 编辑器](https://www.rfc-editor.org/rfc/rfc9421.html) 对 Zeon，我建议保留一个由客户端生成、纳入签名的 `request_id`：同一请求重试时返回原来的 commit，而不是再次产生事实；同一个 ID 配上不同内容则拒绝。对于 `iterlist`，这能避免“第一次投币其实成功了，但响应丢失，重试后又投了一次”。

还有一个可以暂时记下的细节：时间窗口究竟比较服务端接收请求的时间，还是排队结束、进入提交处理的时间？沿用你现在的后者也可以，但那意味着排队过久会使请求过期。这个行为需要是有意规定的，而不是将来负载稍高时才偶然发现。

## 缓存可以落后，但不必暴露半个 commit

你说“当前状态本身就是缓存”，我很认同。它把事实来源与服务读取的结构分开了。不过，缓存的可重建性和它对外承诺的一致性，是两件不同的事。

我建议把普通读取的允许范围表述为：**可以看到较旧的完整状态，但同一次读取不应看到一个 commit 应用到一半的状态。** 这并不要求所有缓存、所有客户端同时看到最新 commit；它要求的是，在某个读取视图内部，commit 的变化作为整体出现。

先按单链模型考虑，一个缓存可以声明自己已经完整应用到 `C42`。它暂时没有应用 `C43` 没有关系，但不能已经更新 `C43` 中 pair 的一侧，却仍然返回另一侧的旧值。

你计划的 SQLite 存储层次很适合先把这个问题处理得直接一些：原始 commit、修改记录、作为基础读取来源的 current state，以及对应的 head，初期都可以在同一个 SQLite database 的同一个 transaction 中更新。其他连接在正常隔离设置下不会读到这份 transaction 尚未提交的部分修改。[SQLite](https://www.sqlite.org/isolation.html?utm_source=chatgpt.com)

这里，原始 commit 可以被明确指定为事实来源；暴露修改指针各字段的表，是便于检索的展开形式；current state 则是进一步的解释结果。后两者即使需要重建，也不改变已经接受的历史。没有必要因为它们在概念上都是派生结构，就要求它们从第一版开始全部异步更新。

对于以后独立的内存缓存或缓存服务端，可以让缓存先在不可见的区域完成一整个 commit，再发布新版本；或者用缓存自己的 transaction、读写锁等方式隔离更新。特别要注意，**仅仅在最后更新一个 `applied_position` 标记是不够的**：如果数据已经原地改到一半，又没有隔离读者，读者仍然能看到中间状态。那个标记必须对应一个确实能够被固定、完整读取的版本。

同样，一次查询如果把 `C42` 的对象缓存与 `C45` 的 reducer 缓存拼起来，整体未必对应历史上任何一个完整状态。因此，“事务读取”最简单的初期实现，是绕过这些可能不同步的派生缓存，直接读取基础 current state 的同一个 snapshot。

你设想的串行通道还可以做得更轻一些：**让“确定读取 snapshot”经过串行通道，不一定让整个查询执行过程都占用串行通道。** 例如处理完 `C42` 后，为读取请求建立并固定 snapshot，然后继续处理 `C43`；读取请求仍然在自己的 snapshot 上完成查询。SQLite WAL 下的 read transaction 正好可以保留这样的稳定视图。[SQLite](https://www.sqlite.org/isolation.html?utm_source=chatgpt.com)

实现上有个小细节：普通的 `BEGIN` 本身未必已经固定读取 snapshot，SQLite 的 deferred transaction 要到首次实际访问数据库时才真正开始。因此，不能只在通道里执行 `BEGIN` 就放行 writer；应当在该位置实际开始读取，例如读取 head，从而确立边界。[SQLite](https://www.sqlite.org/lang_transaction.html) 也不能只记下 `C42`，随后再去一个已经被覆盖到 `C43` 的无版本缓存里读取。

最后，既然“已接受历史永不丢失”是重要承诺，成功响应的边界需要包括 durability，而不只是内存里已经接受。SQLite WAL 的 `synchronous=FULL` 与 `NORMAL` 在掉电后的持久性保证上有区别；我会把前者作为初期评估基线，而不是先追求减少同步写入。当然，底层文件系统和存储设备仍需正确兑现同步语义。[SQLite](https://www.sqlite.org/wal.html)

## 关于 branch，我更想先分清你希望“回滚”恢复什么

你现在的纠结很有道理，因为对 Zeon 来说，“补一个反向 commit”确实不是通用答案。我会把回滚涉及的事情分成三种，但不把它们混成一个操作。

**查看过去的状态，不需要 branch，也不需要 clone 整个 repo。** 只要历史保留，就可以为某个 commit 建立只读视图。实现上可以 replay 到那里，也可以使用 checkpoint 加后续增量；这些都是缓存策略。这里说的是 Zeon 的历史视图，并不是依赖 SQLite 永久保留旧 snapshot。

**在现有历史上纠正某个错误，可以通过新的 commit，但未必能严格恢复过去的完整状态。** 例如 `mut` 可以提交旧值，pair 可以重新连接；但已经提交的 `const` 不能随意改回去，`iterlist` 里已经发生过的贡献也不会因为一个新值而消失。甚至恢复不同 operator 的 `iterset` 贡献，也涉及谁有权代表谁提交。按现有属性语义，并不存在一个天然适用于所有 commit 的逆运算。

**从某个过去状态重新开始写入，同时保留后来已经发生的一切，才真正触及 branch 或 fork。** 你提到“clone 从头到某个 commit 的仓库”，实际上是在新 repo 里承载这条新的演化路径。branch 则是在原 repo 内表达同一件事。

就你描述的这一种回滚而言，我会更偏向一个极简的 branch 模型，而不是要求每次都创建完整的新 repo，也不强求用补偿 commit 假装历史没有发生。它不必同时带来 merge、rebase、cherry-pick 或其他复杂操作。

可以先只允许这样的结构：

```
C1 → C2 → C3 → C4       branch A，完整保留
      └────→ C5         branch B，从 C2 继续
```

所谓回滚，不是把 A 的 head 从 `C4` 往回挪、使后续提交失去归属，而是在 `C2` 建立 B，再把默认使用的 branch 切换到 B。A 可以归档，但其归属关系仍然保留。新 commit 的接受与 branch head 的前进在同一个 transaction 内完成，也就不会出现“commit 已经存进去，但尚未挂到任何 branch”的对外状态。

这样，“不允许 dangling commit”可以成为一个明确的 invariant：任何允许的 branch 操作都不得使已有 commit 失去所有归属。最简单的初期规则就是 branch 只允许追加和归档，不允许破坏性回退 head，也不允许删除会导致提交失去归属的 branch。选择哪个 branch 作为默认视图的变化，也可以被记录下来，而不是成为一项不留历史的管理操作。

但这里确实有一个模型上的代价，需要认真决定：**引入 branch 后，“repo 接受 commit 的全局顺序”和“某个状态的历史路径”将不再是同一件事。** 上图中 `C5` 可以是全 repo 第五个接受的 commit，但它的 candidate state 基于 `C2`，不是基于 `C4`。不能再把所有 commit 按 ID 排序、依次应用，就得到某个 branch 的当前状态；还需要明确的 parent、base 或等价的 lineage 信息。

这并不违反你说的“每个 repo 有一个权威状态”。repo 仍然可以只有一个权威的历史结构与 branch 元数据，也仍然只有一个串行写入通道；只是业务数据视图需要指定 branch，或者使用唯一的 active branch。两个 branch 的写入同样可以完全串行，branch 与并发写没有必然绑定。

另外，一旦允许切换 active branch，客户端的提交最好明确绑定目标 branch，而不是在服务端接收时才解释为“当前默认 branch”。否则一个在回滚前发出、因网络延迟而晚到的请求，可能意外落到回滚后的新路径上。这个 branch identity 也应属于客户端签署的请求内容。

所以，我对这一轮几个选择的倾向是：保留 single writer，把权威接受顺序从 wall clock 中独立出来；初期让基础 current state 与 commit 一起事务性落库，再逐步增加异步缓存；历史读取与纠错提交先分别定义，而真正“从过去重新出发”的能力，可以用不允许遗弃历史、暂不支持 merge 的极简 branch 来表达。

接下来我最想听的是一个更接近你原始模型的问题：**你希望回滚是在同一条演化历史上记录一次纠正，还是承认世界从过去的某一点分出了另一条路径，而原来的路径仍然真实地保留着？** 这两者都能保持不可变性，但它们赋予 repo 的含义不一样；先认清你更认同哪一种，branch 的取舍就会自然很多。
