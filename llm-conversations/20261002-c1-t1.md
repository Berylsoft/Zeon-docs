# USER

我们接下来要讨论我的个人项目Zeon的设计与实现。Zeon是一个模型介于关系型数据库和非关系型数据库之间的，以不可变性为核心特点的，不仅作为数据库还作为整个后端的「插排」的数据平台。Zeon的目前已成型的文档在`https://github.com/Berylsoft/Zeon-docs`中，截至本轮对话开始前最新的提交为fa1d8e0。请仔细阅读`concepts.md`、`best-pratices.md`、`bcbc-spec.md`（注意要读markdown注释内容）三个文件，并谈谈你眼中的Zeon是一个什么样的项目，并列出你想知道的还没有在文档中落实的Zeon设计（例如通讯协议等）。

# LLM

我对 Zeon 的第一判断是：**它不是在“关系型数据库”和“文档数据库”之间取一个折中点，而是在尝试建立一套统一的数据世界模型；数据库是这个模型的持久化与查询内核，“后端插排”则是它向外延伸的运行时形态。**

如果用一句话概括我眼中的方向：

> **Zeon 是一个以对象承载身份、以 trait 描述数据与能力、以带操作者身份的 commit 记录变化，再通过校验和派生机制组织后端行为的、以可追溯性为基础的数据平台。**

这里面有些已经在 `fa1d8e0` 的文档中相当清晰，有些还是我根据现有概念作出的架构判断。尤其是“后端运行时”和“插排”的具体边界，三份文档还没有正式定义。 

## 一、我眼中的 Zeon，最有特点的是什么

### 1. 它先追求模型的自洽，再寻找模型的用途

`concepts.md` 的开篇对理解项目很重要：你并不是先列出一组市场需求，再组合已有技术满足它们，而是先描摹一个你认为正确的“世界式”。所以，我不会首先用“它要取代哪种数据库”“它有哪些竞品没有的功能”来评价它；我更在意的是：**这套模型能否用少量稳定概念，解释越来越多的实际情形，而不需要不断添加例外。**这是我从开篇读出的设计取向。

在这个取向下，不可变性、唯一性、透明性和模块化并不是四个互不相干的功能标签，而可能是同一个目标的不同侧面：让身份、事实、规则、当前状态之间的关系尽量明确。

不过，后三项目前基本还是哲学标题，我不会替你把它们解释成已经确定的技术约束。例如，“唯一性”究竟意味着身份唯一、表示唯一，还是同一事实不应有多份独立维护的来源，文档还没有给出答案。

### 2. 对象、trait、提交分别回答不同的问题

我觉得现有模型最干净的地方，是把几个容易混在一起的问题拆开了：

**对象回答“是谁”。** 对象具有由对象类型 ID 和类型内 ID 组成的身份；实际数据与功能通过 trait 附着。至于“对象自身是否严格等同于一个 ID”，原文仍然留了问号，不能把它当作已经定稿的实现约束。

**对象类型回答“这个身份至少必须具备什么”。** 它不直接等同于一张固定字段表，而是规定必需 trait 集合。

**trait 回答“具有什么数据，以及这些数据怎样变化”。** 它不只是字段分组，因为属性声明已经包含了提交的解释方式。

**commit 回答“谁在什么时候，对哪些位置作了什么提交”。** 对象是空间维度的单元，提交是时间维度的单元；操作者又作为对象进入了这个世界，而不是只存在于数据库外部的登录系统中。

因此，我更愿意把 Zeon 理解成一种**基于身份与能力组合的、有明确 schema 的对象模型**，而不是“部分字段结构化、部分字段随便放”的混合数据库。

它的灵活性似乎来自 **trait 的组合**，而不是放弃类型和约束；它的关系性则体现在对象引用、`pair` 等对象间约束上，而不是必须先以表和外键来组织世界。

### 3. 真正有辨识度的是“属性的提交语义”

六种属性类型是我认为最值得继续打磨的部分：

| 属性类型 | 我对其核心语义的理解 |
| --- | --- |
| `const` | 第一次提交确立值，后续提交不能改变它。 |
| `mut` | 可见值取最新提交的值。 |
| `iterlist` | 历次提交的值构成列表，并能按操作者取得其提交历史。 |
| `iterset` | 每个操作者保留一个最新贡献；整体由这些贡献组成。 |
| `pair` | 一次关系变更必须满足两个对象之间的对应约束。 |
| `complex` | 提交增量，通过累积应用 diff 得到复杂值。 |

这是根据文档作出的语义归纳；具体排序、冲突处理和 diff 规则仍未定义。

这里尤其需要强调两个区别。

**第一，`mut` 的“覆盖”不必意味着历史事实被覆盖。** 按照你的不可变性目标，最自然的理解是：变化发生在“当前可见值”上，而历次被接受的提交仍是事实。这是我对设计方向的理解，还不是文档已经写完的存储保证。

**第二，`iterset` 不是普通的值去重集合。** 更接近的概念模型是：

```
操作者 → 该操作者最新提交的值
```

两个人都提交 `some(true)`，应当是两个点赞，而不是因为值相等而合并为一个元素。点赞示例正好把这一点表达得很清楚。相应地，`iterlist` 也不同于“一个可以整体覆盖的列表字段”：它将操作者的历次贡献直接纳入属性语义。 

所以，Zeon 不只是给值附带一份审计日志，而是在尝试让**历史和贡献者身份参与定义值本身是什么**。

### 4. 最佳实践展示的是“声明领域行为”，而不只是数据存储

点赞和投币两个例子，比单纯的概念定义更能体现项目意图。

点赞的每人状态由 `iterset` 表达；是否允许点踩由 validator 限制；总点赞数、净分和分别统计由 reducer 派生。投币则用 `iterlist` 保留每次贡献，用按操作者的 reducer 计算累计值，再让 validator 检查上限。文档还提出把这些常用 validator/reducer 收入标准库。

我从中看到的目标是：

> **让“结构、合法变化、派生结果”能够在同一套模型中声明，而不是要求每个应用分别维护数据表、业务判断和统计字段。**

这也是“插排”定位最有说服力的起点。我的理解不是让 Zeon 内置所有后端功能，而是让各种功能接入时，可以共享同一套身份、类型、提交和约束语义。

但需要保留一个边界：**现有文档已经展示了数据与行为结合的方向，还没有说明这些行为究竟运行在哪里、以什么形式编写，以及外部模块如何接入。**

### 5. BCBC 看起来是在为统一的数据边界做准备

BCBC 不只是“把几个数据库字段序列化”的格式。它明确区分了基础值、泛型类型、自定义类型、类型值和类型 ID；空列表与空 `option` 仍携带元素类型信息；自定义值携带类型 ID，适用时还携带泛型参数。字符串则按 Unicode 标量值序列编码，而不是直接规定为 UTF-8 字节串。

我的判断是：这套设计很适合承担 **Zeon 内部与外部组件之间的共同数据语言**，而不仅是磁盘格式。

不过，它不能因此被直接称为“完全自包含的 schema”：读到自定义类型 ID，不等于已经知道其字段定义、枚举含义或约束。类型定义的获取与解析仍然需要另一层机制。

注释也透露了几个很有价值的方向：
- `unit` 对迭代属性有用，让我想到“提交的意义主要来自谁在何时做过某事，而不需要额外载荷”的建模方式。
- alias 可以附加 validator，意味着它可能承载的不只是命名，还包括受约束的数据概念。
- trait ID 是否与类型 ID 统一，触及的是整个扩展体系的身份模型。
- BCBL 的无限列表只出现在注释里，不能据此认为 BCBC 的 `list` 已经具有无限流语义。
另外，注释并不全是待定问题。例如 tuple 在 schema 中不采用泛型写法，以及 `option` 选择 `is_some` 的理由，更像是已有设计的说明；无泛型参数时是否省略编码、第三方类型 ID 如何表示，才是明显尚未落定的部分。

## 二、我最想了解的、尚未在这三份文档中落实的设计

下面的“未落实”仅指**这三份文档还没有形成明确约定**，不代表你尚未思考过。我会按对其他设计的影响程度来排列，而不是把通信协议当作一个孤立的技术选型。

### 1. 一个 commit 究竟如何成为“已接受的事实”？

提交已经有 ID、签名、附加信息和属性定位方式，`pair` 还明确要求两侧处于同一个提交中。但这些定义尚不足以确定完整的事务语义。

我首先想知道：一个 commit 是否整体成功或整体失败？校验面对的是提交前的状态，还是应用整份提交后的候选状态？客户端能否声明“仅当我读到的版本仍然有效时接受本次提交”？

投币案例可以直接检验这个问题。**假设**某操作者累计投币为 1、上限为 2，两个并发请求各投 1：两次 validator 都读到旧值 1 时，不能仅靠各自通过检查就保证最终不超限。这里需要确定冲突检测或串行化规则，而不只是 validator 的计算公式。

此外，提交 ID 中的时间戳是谁生成的？“第一次”“最新一次”按客户端时间、服务端接收顺序，还是某种正式提交顺序确定？防碰撞序列码并不会自动回答这个排序问题。

### 2. 六种属性类型，是互斥分类，还是几组可以组合的性质？

这是我认为概念层最值得澄清的问题之一。

目前六类属性实际上承载了不同维度：`const`、`mut`、`iterlist`、`iterset` 主要描述历史与操作者如何决定可见值；`pair` 主要描述跨对象一致性；`complex` 则还涉及变更的表达方式。`defaultable` 已被设计成可以附加的性质。

那么，`pair` 是否天然具有类似 `mut` 的更新行为？能否有不可变的成对关系？复杂值能否按操作者保存不同贡献？这些能力是有意互斥，还是未来允许组合？

具体到两种特殊属性，还需要正式规则：

**`pair`：** 指针目前只描述目标对象 ID；目标对象有多个 pair 属性时，怎样确定对应端？从 A—B 改为 A—C 时，需要怎样处理 B 的旧指向？

**`complex`：** diff 针对什么数据模型、以哪个版本为基准、基准过期时如何处理？“可以保存 diff”本身，并没有规定并发合并规则。

### 3. 对象和 trait 的生命周期如何进入提交模型？

目前提交体的键可以定位“对象—trait—属性”，但对象创建、附加 trait、移除 trait、删除对象等操作的表示方式还没有明确。

我想知道：这些生命周期变化也是特殊的属性提交，还是需要专门的操作类型？对象创建与必需 trait 的初始化是否必须在同一提交内完成？移除一个 trait 后，历史查询是否仍能访问它？重新附加时，是延续原历史，还是开启新的实例？

另外，“没有提交过一个属性”“提交过 `none`”“使用默认值”不能不加区分地视为同一种状态。点赞示例在用户界面上可以将未操作与主动恢复初始值都显示为中立，但提交历史显然不同；查询接口需要决定在哪些层次保留这种区别。 

### 4. 历史值究竟由哪个版本的 schema、默认值和规则解释？

trait versioning 仍是占位内容；属性 ID 又按 schema 顺序编号；对象类型的必需 trait 集合可以通过 migration commit 修改。它们组合起来后，版本语义会直接影响历史是否仍然可解释。

我关心的不只是“是否支持迁移”，而是：属性重排是否允许？删除的编号是否保留？类型变更产生新版本还是新身份？旧 commit 如何确定当时使用的定义？

默认值尤其值得单独推演。**假设**对象创建时省略了一个可默认属性，类型默认值后来从 5 改为 10：查询这个对象的当前值是什么？查询创建时的历史值是什么？如果属性同时是 `const`，省略提交算不算已经确立了它的值？

还有文档注释里已经提出的 migration 作者问题：实际业务主体、授权迁移的人、执行迁移的程序是否是不同角色？它们与提交 ID 中的单个操作者是什么关系？我不会预先假定必须支持多操作者，但需要明确这些责任如何表达。

### 5. validator 和 reducer 的执行模型是什么？

最佳实践已经大量使用它们，但还没有正式定义其输入、输出、执行环境及生命周期。代码块标记 `bcs`，以及注释出现的 BCBL，也尚未在这三份文件中说明它们与 schema、校验和计算之间的关系。 

我想了解：它们是声明式表达式、内置函数组合，还是可以运行用户程序？能读哪些对象？是否必须确定、无副作用？如何限制运行时间、内存以及递归？规则本身如何版本化？

这里还有一个直接关系正确性的细节：**对 `iterset` 做聚合，不能无条件把每次新提交都当成新增元素。** 同一个人从赞改为踩，聚合需要移除旧贡献并加入新贡献，或者重新计算当前贡献集合。文档里的 reducer 描述足以说明“遍历当前集合时怎么算”，但尚未规定物化结果如何增量维护。

因此，我想区分两件事：reducer 的数学含义，以及执行引擎维护结果的方式。它们不必是同一个接口。

### 6. 查询面对的是哪一种视图？

文档已经区分按操作者查询、直接查询 reducer 结果，以及会解释默认值的“非提交查询”，但完整查询模型还未定义。 

我想知道：查询语言或查询对象长什么样？能否按 trait 查询跨对象类型的对象？能否过滤关系、关联对象、查询历史或定位到修改指针？

更关键的是一致性：一次查询中的原始值、按操作者视图、默认值和 reducer 结果，是否保证来自同一个快照？若索引或 reducer 异步更新，客户端怎样识别其进度？

我会倾向于先把“提交记录”“属性解释后的状态”“进一步派生的结果”区分清楚，再决定 API 如何呈现，而不是让它们都以一个含义模糊的 `get` 暴露出来。

### 7. 操作者、权限和签名之间如何连接？

操作者是对象，提交头含签名，但认证、授权和签名的关联尚不明确。

一个登录会话怎样取得代表某个 operator 提交的权利？后台服务替用户提交时，以谁为操作者？权限控制到对象、trait 还是属性？读取历史、按操作者查询、读取聚合值，是否有不同的权限？

签名则需要确定签署者、覆盖范围以及验证方式。如果附加信息含有服务端记录的来源 IP，客户端签名是否覆盖这些字段，就需要明确安排。

重放也与此有关：权限已经撤销之后，历史上被合法接受的提交应如何回放和审计？应用已接受历史，与按当前权限重新批准一次操作，是两个不同的问题。

### 8. 通信协议准备承担哪些语义？

**BCBC 定义了值怎样编码，但还没有定义客户端与服务端怎样对话。** 现有类型体系与提交结构不能直接替代完整的通信协议。 

我想先明确操作层：提交、查询、获取 schema、订阅变化，分别是什么请求和响应？提交成功返回的是“已经收下”“已经持久化”，还是“所有相关视图都可读”？连接中断后，客户端如何判断某个提交是否已经成功，而不导致重复提交？

之后才是传输层选择：基于现有 HTTP/WebSocket 等承载，还是原生协议；如何分帧、协商版本、处理大型结果和流式数据。

如果支持订阅，还需要游标、断线续传、背压和重放规则。外部组件拿到一个第三方类型 ID 时怎样获取定义，也应当与协议一起设计。

### 9. “插排”的插口究竟是什么？

这是项目定位中最重要、但目前最少被具体说明的部分。

我想知道你希望接入的单位是什么：一个 trait 包、一组 validator/reducer、一个进程内模块、独立服务，还是订阅提交的消费者？这些扩展共享哪些契约，能否互相依赖，怎样安装、升级和停用？

其中需要划清一条边界：**参与数据合法性判断的同步逻辑，与发送通知、调用外部服务等副作用，不应在模型里含混处理。**

例如提交已落库但通知没有发送成功，Zeon 如何表示和恢复？外部模块根据提交产生另一个提交时，如何记录来源、避免重复执行或反馈循环？

我的理解是，“插排”的价值应当来自这些稳定契约，而不只是“有插件接口”；不过，这仍需要你的正式定义。

### 10. BCBC 的类型身份、等价性和解码规则如何闭合？

这里有几项已经被正文或注释直接点出了：第三方类型 ID 的编码未定；类型 ID 是否兼作 trait ID 未定；无泛型参数时能否省略相应结构也仍在讨论。

我还想了解这些相邻问题：匿名自定义类型如何取得其定义？alias 是纯别名，还是具有独立身份的名义类型？禁止直接自别名之外，间接别名环如何处理？`map` 用列表表达后，重复键和元素顺序是否具有语义？

编码层则需要明确非最短整数编码、非法布尔值、无效 Unicode 标量、嵌套深度和总解码预算等边界。已有分类型长度限制是重要基础，但还需要整体资源约束。

签名不一定要求所有值只有一种编码——签署原始字节也是一种方案；但**到底签原始字节还是规范化结构，以及等价编码是否代表同一个逻辑提交，必须说清楚。**

### 11. 不可变性的承诺延伸到哪里，存储与部署准备怎样实现？

最后，我想知道“不变”的准确对象：已接受提交不可修改？不可删除？允许只保留快照而裁剪旧历史吗？允许逻辑删除但禁止物理清除吗？回滚是增加补偿提交，还是允许将某个视图指向旧状态？

这些答案会决定提交记录、当前状态、索引、reducer 缓存和快照之间，谁是事实来源，谁可以重建。

部署方面，repository 的定义还留有问号；提交序列码考虑了多机器接收时的碰撞，但这并不等于已经确定了复制、分片或多写者协议。

因此，我想知道首个实现是单机服务、嵌入式库，还是从一开始就具有多节点语义；底层存储准备自建到什么程度；成功确认对应怎样的崩溃恢复保证。这些都应该服务于前面的模型，而不是由底层技术反过来意外决定它。

## 三、我的总体评价与讨论起点

我认为 Zeon 目前已经形成了一个很有辨识度的核心：

**对象组织身份，trait 组织能力，commit 组织历史，operator 组织贡献，validator 和 reducer 组织合法性与派生结果。**

最值得保留的，不是某一种具体存储结构或协议，而是这几者能够放在同一套模型中理解。最需要警惕的，则是表面统一以后，时间顺序、规则版本、默认值、权限与聚合各自暗含不同的“当前状态”，最终让同一份历史产生互相矛盾的解释。

因此，下一轮我最建议从**一个 commit 的完整生命周期**开始：它如何被构造、获得身份、校验、排序、接受、持久化，并让查询与扩展观察到。用点赞改踩、并发投币和一对关系改绑这几个现有例子走通这条路径，会比立即选择通信协议或存储引擎，更快地把 Zeon 的核心设计落实下来。
